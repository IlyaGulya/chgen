# Checking and server-assisted discovery

These tools separate generation readiness, measured inference, and client
assertions. They do not promise complete ClickHouse dialect coverage.

## Offline project check

```sh
chgen check -f chgen.yaml -json
chgen check -f chgen.yaml -require-confirmed
```

The command runs the same planning phase as generation, including schema
replay, query resolution, Go emission, and output path/collision validation.
It never commits generated bytes, creates output directories, or contacts a
server. Like `Run`, it stops at the first failure; failure counts are not a
partial-project coverage report. A successful check does not check whether
committed generated files are stale: generate and inspect the diff for that.

`can_generate` and `status` answer different questions:

| Status | Meaning within chgen's model |
| --- | --- |
| `confirmed` | Planning succeeded without the reported inference escape hatches. Not a proof of all SQL semantics. |
| `invalid` | A classified contradiction, such as an asserted type conflicting with inference or a measured invalid operand pair. |
| `unknown` | Missing coverage, an unclassified refusal, or an explicitly accepted client assumption. Unknown is not invalid SQL. |

Without `-require-confirmed`, the exit code follows generation readiness:
zero for success (including explicit assumptions), one for failure. Strict
checking also returns one when readiness depends on assumptions. Invalid CLI
arguments return two. `-json` writes the report to stdout even on a project
failure. Flag errors go to stderr.

Diagnostics carry a stable code, status, stage, message, and next-step hint.
Package and query source context are included where available; query locations
identify the `-- name:` declaration, while message text may name a more precise
annotation line. Classification is attached at the cause and retained through
error wrapping, never inferred by matching English strings.

Current specific codes include `function-rule-missing`, `setting-unmeasured`,
`query-parser-refusal`, `schema-parser-refusal`, `schema-operation-unmodeled`,
`result-contract-conflict`, and `comparison-domain-{unmeasured,invalid}`.
Unconverted errors deliberately remain `unclassified` / `unknown`; coverage
of diagnostics is incremental, not an assertion that every refusal is typed.
Callers should tolerate new codes.

Successful plans expose `result-type-asserted` only when inference actually
needed the client contract, and `setting-unchecked` only for opted-in names
not yet in the measured roster. A matching inferred type or a setting now
covered by a built-in rule does not become an unknown just because its old
annotation is still present. Known setting validation always wins.

Go callers use `Check(configPath) (CheckReport, error)` and `ExplainError(err)`.
The error still supports `errors.Is` and `errors.As`; it is not replaced by
the report. `ExplainError(nil)` returns an empty diagnostic.

## Explicit server assistance

```sh
chgen describe -server http://localhost:8123 \
  -database fixture -sql concrete-select.sql
```

Use an explicitly chosen test instance, existing fixture tables, and a
restricted read-only account. Authentication is read from
`CHGEN_DESCRIBE_USER` / `CHGEN_DESCRIBE_PASSWORD`, not command-line flags.
Credentials and query parameters are rejected in the endpoint URL.

The input must be one concrete SELECT, without FORMAT. Replace application
parameters with representative typed values and supply existing fixture
relations instead of `chgen.external` markers. This version does not bind
application arguments, create external tables, or replay migrations. Parser
coverage remains a prerequisite for the local statement guard.

The tool sends a version query and `DESCRIBE TABLE (SELECT …) FORMAT JSON`,
with `readonly=1`, bounded request time and response size, and redirects
disabled. It does not execute the source SELECT for result rows or apply DDL.
Analysis can still evaluate constants and contact table-function data sources:
read-only analysis is **not a sandbox for hostile SQL or a guarantee of zero
I/O**. Do not point it at production merely because it uses DESCRIBE.

The JSON report records `provenance: server-analysis`, the observed version,
the SHA-256 of the exact input bytes, and result columns. Simple unique names
with supported Go mappings get candidate `-- result-chtype:` annotations.
No annotation is inserted into files automatically. A suggestion is syntax,
not a guarantee of eligibility: outer-result annotations retain their alias
and argument-validation restrictions. For intermediate calls, use a local
[expression contract](expression-contracts.md) at the expression instead.

For example, `intDiv(number, toUInt64(2)) AS bucket` over a real UInt64 column
can acquire a UInt64 contract without a release that adds `intDiv`. This
does not register the function or justify all other argument combinations.
Prefer real fixture columns to literals because constant folding can conceal
execution-only refusals. Keep a value/driver test for critical queries and
repeat verification when the schema, settings, expression, or server changes.

Server analysis is distinct from the existing generated runtime metadata
check, which remains enabled for asserted outputs. Neither proves business
meaning or correct empty-aggregate handling.

Primary references: ClickHouse [DESCRIBE](https://clickhouse.com/docs/reference/statements/describe-table)
and [HTTP interface](https://clickhouse.com/docs/concepts/features/interfaces/http).
The concrete subquery form above is exercised on the pinned 25.8.29.51 server.

## Development contract

Before fixing another missing spelling, identify the affected layer:
parser, catalog effect, scope/binding, inference domain, Go mapping, or runtime.
Record a complete client scenario under `testdata/scenarios/<name>/` with
`schema.sql`, `queries.sql`, and `expect.json`; the public-API corpus discovers
all directories automatically. Keep accepted and refused neighbors. New
family rules still need real-column type **and execution** witnesses.

Run fixed scenarios, generated-driver tests, and the exploratory four-seed
oracle independently. A shuffled population does not replace the fixed bug
witness. Do not accept new mismatch signatures just to make a refactor green.

This increment closes unknown-comparison acceptance, exposes trust and
refusal reasons, reduces duplicate dispatch/evidence lists, and gives clients
a bounded discovery path. Local expression contracts and
[finite typed composition](query-composition.md) extend these boundaries without
pretending that client assertions are measured rules. Full diagnostic coverage,
broader type-domain modeling and general dynamic SQL remain separate work;
neither a global allow-all flag nor automatic SQL rewriting substitutes for
their semantics and tests.
